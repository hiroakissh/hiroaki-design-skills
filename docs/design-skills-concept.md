# Hiroaki Design Skills 構想案

作成日: 2026-10-31 / 更新日: 2026-11-01 / 状態: 初版6スキルにWatch用を追加、7スキルとAtmospheric Graphite v1.0を実装

## 目指す体験

一つのリポジトリで、自分のデザイン判断を育てて管理する。利用するプロジェクトには、その用途に必要なスキルだけを導入する。

たとえば「ネイティブアプリ」「Webアプリ」「調査レポート」で、それぞれ一つのスキルを選べる。アプリのモーションだけを改善したい場合は、専門スキルを追加できる。全スキルの一括導入や、共通スキルの別途インストールを前提にしない。

プロジェクト構成は合意済み。初版の6スキルと、追加のWatch用を実装し、READMEからLight/Darkの実表示と操作できるHTMLを確認できる。以下は拡張候補を含む構想であり、現在の使い方と実装範囲はREADMEを参照する。

各作者の美意識をそのまま個人の好みとして採用しない。文章・コード・資産を転用するときは、個別のライセンスと出典を確認して記録する。たとえば unslop はREADMEでCC BY 4.0とクレジットを案内し、Anthropicは文書系スキルの扱いが他と異なることを明記している。

## 設計の軸

### 1. 成果物ごとのスキルを主な入口にする

ユーザーが選ぶときは、「何を作るか」で選べるようにする。

アプリのナビゲーション、Webアプリの高密度なデータ操作、レポートの根拠の示し方は別の判断である。同じフォント・余白・レイアウトを全用途に押し付けず、共通にするのは判断の姿勢と品質の基準にする。

### 2. 専門スキルは単独でも追加でも使える

モーション、文章、図表、アクセシビリティなどを、独立して依頼できる単位にする。

用途スキルには通常の品質を確保するために必要な内容を含める。専門スキルは、その領域を深く扱う場合に使う。「Webアプリを作るには追加で7スキル必要」という設計にはしない。

### 3. 共通方針は管理上の共通ソースにする

共通方針は、全員が別途導入する必須の基礎スキルにはしない。作者側では一か所で管理し、配布時に各スキルへ必要な内容を含める。

これにより「一か所を直せば全用途へ反映できる」と「一つだけ導入しても動く」を両立する。

## スキルの全体候補

名称には `hiro-design-` を付け、一般的な `frontend-design` や `pdf` との名前の衝突を避ける。以下は拡張先を含むカタログ案であり、すべてを初回に作る予定ではない。

### 専門領域を深く扱うスキル

| スキル名案 | 単独で依頼できる仕事 |
| --- | --- |
| `hiro-design-system` | トークン、コンポーネント、状態、再利用ルールを整理する |
| `hiro-design-motion` | 操作への応答、画面遷移、動きの必要性と性能を改善する |
| `hiro-design-typography` | 和文・欧文・数値の書体、階層、組版、読みやすさを整える |
| `hiro-design-ux-writing` | ボタン、入力説明、エラー、空状態などの文章を整える |
| `hiro-design-dataviz` | 比較目的に合う図表、軸、単位、注記、色の意味を設計する |
| `hiro-design-accessibility` | キーボード、読み上げ、色、拡大表示などを重点的に点検・改善する |

分割する基準は「単独で依頼する機会がある」「独自の判断・成果物・検証がある」こと。同じ手順で扱える小さな違いは `references/` に置く。たとえば管理画面の種類や、レポートの業界ごとに別スキルを量産しない。

## 自分専用にするための共通ソース

共通方針には、次の二種類を区別して記録する。

- **品質の基準:** 情報の優先順位、意味を持つ色、実データでの確認、操作状態、可読性、根拠と出典の扱いなど。
- **個人の好み:** 好きな表現と理由、避けたい表現と理由、情報密度、余白、書体、色、文体、動きの強さなど。

個人の配色はAtmospheric Graphite v1.0を採用済み。書体・余白・状態別トークンなどは未確定であり、参考元やサンプルの値を個人の決定として扱わない。

好みは、参考URLや画像だけでなく「何が良いのか」「どの用途では使わないのか」と組にする。たとえば「高密度な表が好き」は業務ツールでは有効でも、一般向けLPへそのまま適用する理由にはならない。

明示された依頼とプロジェクトの既存ブランド・デザインシステムを確認したうえで、指定がない部分に個人の方針を適用する。機能上の要件やアクセシビリティも合わせて判断する。スキル同士の衝突は、読み込んだ順番で解決しない。

同じルールを改訂するときは、対応する各配布スキルを同じリリースで再生成する。導入済みのコピーへの反映には更新操作が必要であり、元リポジトリの変更が自動で届く前提にはしない。

## リポジトリの構成案

```text
hiroaki-design-skills/
├── README.md                    # 用途別一覧、導入・利用例、プレビュー
├── AGENTS.md                    # 変更時に守るサンプル更新ルール
├── docs/
│   └── design-skills-concept.md # この構想案
├── source/                      # 作者が編集する元データ
│   ├── profile.md               # 自分の好み・判断基準
│   ├── foundations/             # 共通の品質基準
│   └── skills/                  # 各用途固有の指示・資料
├── skills/                      # 公開・個別導入の対象
│   ├── hiro-design-app/
│   │   ├── SKILL.md
│   │   ├── references/          # 必要な共通方針＋用途固有の詳細
│   │   └── agents/openai.yaml   # Codex向けの任意の表示情報
│   ├── hiro-design-webapp/
│   ├── hiro-design-report/
│   └── ...
├── samples/                     # 個別導入とは独立したサンプル集
│   ├── catalog.json             # スキルとサンプルの対応・段階
│   ├── freshness.json           # 確認時点の入力と成果物の記録
│   └── <skill-name>/            # 固定依頼文・データ・成果物・確認記録
├── scripts/
│   ├── build-skills.py          # 共通内容を必要なスキルへ含める
│   ├── render-samples.py        # スキルを適用したテンプレートからHTMLを生成
│   └── check-samples.py         # 更新漏れ・サンプル不足・READMEリンクの検査
├── tests/                       # 更新漏れの検査が正しく働くことを確認
└── evals/                       # 代表依頼と確認用の成果物・評価基準
```

これは実装時の予定構成。不要な空フォルダやテンプレートは先に作らず、利用するものから追加する。

`source/` と生成処理はこのリポジトリの管理方式であり、Agent Skillsの必須仕様ではない。配布物は標準のフォルダと `SKILL.md` にする。[Agent Skills仕様](https://agentskills.io/specification)

### 単独導入が壊れないための決め事

- `skills/<名前>/` だけを別の場所へコピーしても、指示・参照・同梱資産がそろう。
- 実行時に `../../source/profile.md` や隣のスキルへ参照を出さない。必要なファイルはスキル内に含める。
- 共通方針は用途に必要な範囲だけを配布する。アプリのスキルにレポートの組版規則を含めない。
- `SKILL.md` は目的、使う場面、主要な判断、成果物、検証を短く示す。詳細はリンク先の資料へ置く。
- スクリプトや外部ツールが必要な場合は、指示・資産の自己完結性とは別に、その実行条件を明示する。
- 公開用の `skills/` をコミットしておき、利用者側にビルド環境を要求しない。生成物の手編集は避ける。

## READMEで見られるサンプルと更新運用

各スキルには最低1件のサンプルを用意し、READMEにプレビュー、固定依頼文、確認記録を並べる。サンプルは `samples/<skill-name>/` に置き、スキルの個別導入時には必須依存にしない。

スキルの指示、参考資料、スクリプト、資産を変更したら、毎回、同じ依頼文・データでサンプルを再生成し、実際の表示を確認して同じ変更に含める。共通方針を変えた場合は、影響する全用途のサンプルを更新する。外観が同じ結果になっても、再生成と再確認の記録を残す。

現在はWatchを含む7用途にAtmospheric Graphiteを適用したHTML実装例と、Light/Darkのブラウザ画像を用意する。アプリ・Watchはブラウザ用UIプロトタイプであり、ネイティブ実機の検証済み成果物ではない。資料も実際の形式を明記する。

ローカルとGitHub Actionsで入力・成果物の更新漏れ、スキルに対応するサンプルの不足、READMEリンクを検査する。検査は更新の整合性を確認するもので、デザインの質は表示・操作・書き出しを見て判断する。[サンプル更新ガイド](sample-workflow.md)

## 導入する側の体験

初期は既存の `skills` CLIを使う。用途選択のためだけに独自CLIやnpmパッケージを新設しない。CLIはスキル名の指定、複数選択、対象エージェントの指定に対応している。[CLIの公式リファレンス](https://github.com/vercel-labs/skills/blob/main/docs/commands.md)

公開リポジトリの初版では、以下の用途別コマンドで導入する。現在の対応一覧はREADMEを参照する。

```bash
# このプロジェクトで使うネイティブアプリ用スキル
npx skills add hiroakissh/hiroaki-design-skills --skill hiro-design-app -a codex

# Webアプリ用
npx skills add hiroakissh/hiroaki-design-skills --skill hiro-design-webapp -a codex

# 調査レポート用
npx skills add hiroakissh/hiroaki-design-skills --skill hiro-design-report -a codex

# Webアプリと、重点的なレビューをまとめて導入
npx skills add hiroakissh/hiroaki-design-skills --skill hiro-design-webapp hiro-design-review -a codex

# 公開されているスキルを一覧表示
npx skills add hiroakissh/hiroaki-design-skills --list
```

通常はプロジェクト単位とし、全プロジェクトで使いたい場合は `-g` を付ける。Claude Codeを対象にするときは `-a claude-code` に変える。CLI自体はOpenAI製ではなく、Vercel Labsの配布ツールである。

「アプリ制作セット」などは、初期はREADME上で複数スキルを指定したコマンドとして案内する。独自の `--preset` オプションや、未定義の依存解決機能は前提にしない。

Codex CLI/IDEでの利用例:

```text
$hiro-design-app 設定画面を設計してください。対象はiOSです。
$hiro-design-webapp この管理画面の検索と一括操作を改善してください。
$hiro-design-report この調査結果を、根拠が追える比較レポートに整えてください。
$hiro-design-review この画面を確認し、優先して直す点を示してください。
```

明示指定に加え、用途が合うときの自動選択もできるよう、各スキルの `description` に範囲を記す。Codexはまず名前・説明を見て、選択したスキルの本文を読み、必要な補助資料を参照する。[OpenAI公式のスキルガイド](https://learn.chatgpt.com/docs/build-skills)

標準形式にそろえることと、すべての実行環境で同じツールが使えることは別である。初期はCodexで動作を確かめ、Claude Codeでも確認した範囲を互換性情報として掲載する。ChatGPT等へのプラグイン配布が必要になれば、同じ元データから別の配布物を用意する。

## 各スキルにそろえる内容

1. **使う場面:** 何を扱い、近い別スキルとどう使い分けるか。
2. **入力の読み取り:** 誰が何を達成するのか、既存の方向、対象環境、制約は何か。
3. **判断基準:** どの条件で何を選び、その理由は何か。
4. **制作・改善:** 依頼の範囲に合う成果物を作る。構想の依頼では実装へ進まない。
5. **検証:** 用途に合う方法で、実物の見た目と使い方を確認する。

これは説明の共通骨格であり、毎回ユーザーに同じ質問表を答えてもらう手順にはしない。既に分かっている内容は再質問せず、不足情報が結果を左右するときだけ確認する。

「影を必ず消す」「紫を禁止する」などの表現だけの禁止リストを中心にしない。なぜその表現がその成果物に合うかを判断する。既存の良い成果物は、依頼に沿って必要な範囲で改善する。

### 用途により変わる検証

| 用途 | 確認する成果・状態の例 |
| --- | --- |
| アプリ | 実画面、長い日本語、文字サイズ変更、キーボード表示、空・読込・失敗状態 |
| Webアプリ | 狭い画面、キーボード操作、大量・少量データ、入力エラー、選択・一括操作 |
| Webサイト | 最初に伝わる内容、読み順、実コンテンツ、狭い画面、行動への導線 |
| 調査レポート | 結論と根拠の対応、出典、日付、比較条件、単位、事実と推測、ページ分割 |
| スライド | 発表時の視認性、主張のつながり、図表の意味、書き出した実ページ |
| レビュー | 指摘箇所が特定できるか、影響・理由・修正案があるか、適切な優先順位か |

調査レポートのスキルは、提示された情報と出典を整理し、不足や未検証箇所を明示する。デザインを整えたことを、調査内容の正しさの証明として扱わない。調査の実行は依頼に含まれる場合に行う。

PDFやPPTXの生成・編集、画像生成、ブラウザ操作などは必要に応じて実行環境の機能を使う。このリポジトリでは主に「どう判断し、どう仕上げるか」を持ち、汎用的な文書変換エンジンを作り直さない。外部スキルの導入を暗黙の必須条件にしない。

## 最初に作る範囲

第一弾として、共通方針と次の6スキルを実装する。

1. `hiro-design-app`
2. `hiro-design-webapp`
3. `hiro-design-website`
4. `hiro-design-report`
5. `hiro-design-slides`
6. `hiro-design-review`

共通方針を仮決めしたら、まずアプリ・Webアプリ・調査レポートの3用途で小さなサンプルを作って比較する。操作するもの、読むもの、判断するものの違いで、自分らしさと用途ごとの基準を調整する。その後に残りのスキルを整える。

専門スキルと他の成果物向けスキルは、実際に単独で使う機会と必要な資料が見えた順に追加する。将来の分類は広く用意し、初版の完成条件は絞る。

## 初版の完成条件

- アプリ、Webアプリ、調査レポートをそれぞれ一つの指定で個別導入できる。
- 単独の配布フォルダだけで参照が解決し、共通スキルの別途導入を求めない。
- 共通方針を一か所で変更し、必要な配布物へ再生成できる。
- フォーマット検証、参照切れの検査、生成物の更新漏れの検査を通る。
- 実際の導入先で、意図したスキルを選べることと、近い依頼での誤選択を確認する。
- 代表依頼の成果物で、用途固有の要件を満たすことを確認する。文章の一致だけを評価しない。
- 対応するエージェント・環境・外部ツールの条件を明示する。
- リリースと変更内容を記録し、好みや基準の変更を追える。
- 全実装スキルのサンプルをREADMEから見られ、固定依頼文・成果物・確認記録を追える。
- スキル変更時に毎回サンプルを更新し、共通方針変更時は影響する全サンプルを更新する。
- 更新漏れ・サンプル不足・READMEのリンク不足をローカルとCIで検出できる。

## 今後具体化する個人の方針

配色以外の好みは、具体例と実際のサンプルを使って引き続き調整する。

- 好きなUI・サイト・資料と、良いと思う箇所。
- 避けたい表現と、避けたい理由。
- よく作る成果物と、アプリの対象プラットフォーム。
